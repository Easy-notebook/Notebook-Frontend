## TipTap editor layer and its extensions (Notebook-Frontend)

### Current design
Two notebook editors coexist, selected at runtime by settings. CreateMode.tsx (src/components/Scenario/View/CreateMode.tsx) reads settings.editorSettings.editorType (default 'tiptap', see src/store/settingsStore.ts:200 and the union 'tiptap'|'jupyter' in src/store/models/settings.ts:14). When 'tiptap' it mounts TiptapNotebookEditor; when 'jupyter' it mounts JupyterNotebookEditor.

LIVE TipTap entry: src/components/Editor/TiptapNotebookEditor.tsx (348 LOC). It is a forwardRef component exposing a cell-oriented imperative API (getCells/setCells/addCodeCell/addMarkdownCell/addHybridCell/addAIThinkingCell/addRawCell). It builds the editor via useEditor with extensions from getTipTapExtensions() plus 3 local plugins (CursorStyleExtension, TrailingParagraphExtension, EnhancedCursorPositionExtension from TipTap/config/editorPlugins.ts, 207 LOC). Behavior is driven by hooks under TipTap/hooks/: useCellManagement, useEditorEvents (onCreate/onUpdate/onTransaction/onBlur), useEditorSync (cells->HTML sync via convertCellsToHtml), useKeyboardHandlers, useLinkHandler, useBeforeUnload. Source of truth is the Zustand notebookStore cells[]; the editor converts cells to HTML once on mount (initialContent, empty deps) and syncs back via onUpdate. It also listens to window 'markdown-cell-focus' / dispatches 'cell-navigation' CustomEvents for cross-cell cursor navigation.

ALTERNATE entry (NOT TipTap): src/components/Editor/JupyterNotebookEditor.tsx (729 LOC) renders one React component per cell (CodeCell, MarkdownCell, HybridCell, ImageCell, AIThinkingCell, LinkCell from ./Cells) inside DraggableCellList; it has no ProseMirror/TipTap instance at all (its handle.editor is typed null). It is a parallel implementation, still reachable when editorType==='jupyter'.

Extension wiring (src/components/Editor/TipTap/config/extensions.ts, 152 LOC): getTipTapExtensions() returns StarterKit (document/codeBlock/heading disabled), a custom Document with content 'title block+', Link (with file:// protocol), WikiLinkInput (a local InputRule extension defined in this file), and the custom node extensions imported from @Editor/extensions barrel: CodeBlockExtension, ThinkingCellExtension, FileAttachmentExtension, TitleExtension, ImageExtension, LaTeXExtension, RawCellExtension, UploadDropExtension, plus a custom Heading (id preservation), Placeholder, official Table/TableRow/TableHeader/TableCell, and SimpleTableExtension (keymap helper). config/index.ts just re-exports these.

The barrel src/components/Editor/extensions/index.ts is the indirection that decides which physical files are live: CodeBlockExtension, ImageExtension, LaTeXExtension, ThinkingCellExtension all resolve to the implementations/* versions (BaseExtension.create-based, atom block nodes whose ReactNodeViewRenderer mounts the SAME ./Cells React components used by the Jupyter editor — e.g. CodeBlockView renders Cells/CodeCell|HybridCell, ThinkingCellView renders Cells/AIThinkingCell). FileAttachmentExtension, RawCellExtension, TitleExtension (-> TitleNodeView), UploadDropExtension resolve to the top-level extension files.

### Migration concerns
- The 'document' is not really a ProseMirror document — it is a projection of Zustand cells[] round-tripped through HTML (convertCellsToHtml / markdownConverters). A PM-first migration must invert this: PM doc becomes source of truth and the store derives from it, or the HTML bridge must be replaced with a PM JSON <-> cell model mapping. The once-on-mount initialContent (empty deps) plus onUpdate reparse is a known race/fragility surface.
- Every custom cell is an atom block whose content lives entirely inside a React NodeView that reads/writes the global store. There is no PM-native representation of cell content (code text, outputs, thinking text are JSON-encoded attrs like data-code/data-outputs). Real PM migration would want code/text as actual PM content or NodeView-managed but PM-owned state, not store-coupled React.
- Heavy reuse of the same ./Cells React components by BOTH editors means you cannot delete the Jupyter editor or refactor Cells without touching the TipTap NodeViews, and vice versa.
- Cross-cell cursor navigation is implemented via window CustomEvents and manual doc.descendants position math (see the markdown-cell-focus handler, TiptapNotebookEditor.tsx:177-257, and CodeBlockExtension keyboard shortcuts). This bespoke logic must be reimplemented as PM commands/keymaps/decorations.
- 11 BlockManager variants + 2 duplicate extension trees + dead slash-command implementations mean the live code path must be carefully isolated before migration; risk of porting a dead variant. Only SimpleDragManager, implementations/* extensions, top-level RawCell/FileAttachment/Title/UploadDrop, and TipTapSlashCommands are live.
- Custom Document schema 'title block+' forces a Title-first invariant; any PM schema redesign must preserve or migrate this and the id-preserving Heading parse rules.
- fsmState/ExtensionFSM scaffolding suggests an abandoned state-machine design; decide to adopt or drop before building the PM schema.
- Direct prosemirror-state imports and InputRule/keyboard handlers inside extensions are already PM-level, so those parts port relatively cleanly; the store/React-NodeView coupling is the hard part.

## Notebook/Cell Data Model and Zustand Store Coupling

### Current design
The canonical notebook is a FLAT ARRAY of cells held in the Zustand store: `cells: Cell[]` in notebookStore.ts (NotebookStoreState). There is NO ProseMirror/TipTap document as canonical source of truth — the TipTap editor's HTML/doc is a DERIVED, round-tripped view of the array.

Cell shape (src/store/models/cell.ts): `Cell` = { id: string; type: CellType ('code'|'markdown'|'raw'|'hybrid'|'image'|'thinking'|'link'); content: string; outputs?: OutputItem[]; enableEdit?: boolean; phaseId?: string|null; description?: string|null; metadata?: Record<string,any>|null; [key:string]: any }. The index signature lets UI read arbitrary ad-hoc fields. `content` is always a markdown/code STRING (not structured). A parallel `CellModel` class wraps the same shape with helpers (setContent, appendContent, convertToHybrid, convertMarkdownCodeBlockToCode, setOutputs, sanitizeOutputs, hasError, toJSON/fromJSON). The store stores PLAIN objects, not CellModel instances — it instantiates CellModel transiently inside a few actions then immediately calls .toJSON() to put a plain object into state.

Outputs: OutputItem = { type; content: any; timestamp?; key? }. Store serializes/deserializes output.content (object<->JSON-string) via serializeOutput/deserializeOutput on in/out. Sentinel outputs are injected as data: '[error-message-for-debug]' (prepended when an output has type 'error') and '[without-output]' (when empty), then pattern-matched in UI (CodeCellViewModel.showAIdebug).

Derived structure: tasks: Task[] (Task->phases->steps) is RECOMPUTED from the flat cells array on nearly every mutation via parseMarkdownCells(cells) + updateCellsPhaseId(cells, tasks) (markdownParser), which also mutates phaseId onto cells. Step/phase views (getCurrentViewCells, findCellsByStep) are computed on demand. A default H1 'title cell' (metadata.isDefaultTitle) is auto-maintained as cells[0] and special-cased everywhere (addCell, deleteCell guard, setNotebookTitle, setCells empty-fallback).

Persistence: store cells/tasks are snapshotted as-is into IndexedDB via AutoSaveService (NotebookSnapshot {notebookId, notebookTitle, cells: Cell[], tasks: Task[], timestamp}). A zustand subscribe selector on {notebookId,title,cells,tasks,isInitialized} triggers debounced autosave. notebookOrm.ts manages only the NotebookEntity metadata row (title, access stats, fileCount/size, activities) — it does NOT store cells.

ViewModel relationship: Each cell-type folder has an OOP ViewModel extending BaseCellViewModel, created once-per-component via a useXxxCellViewModel hook (useMemo empty deps + useEffect updateProps + manual subscribe/forceUpdate). The ViewModel holds this.cell (a reference to the store's plain Cell prop) plus LOCAL ephemeral UI state (isExpanded, isHovering, contentHeight, localContent, refs) with its own listener/notify pub-sub separate from Zustand. Critically, ViewModels read/write Zustand and codeStore DIRECTLY via useStore.getState() (BaseCellViewModel: isEditing, toggleEditing, deleteCell, navigateToSibling, focusCell; CodeCellViewModel: debounced updateCell, clearCellOutputs, clearAllOutputs, updateCellType, setEditingCellId, detached/current/showCellIds reads; useCodeStore execute/cancel/cellMode). ViewModels are thin imperative wrappers that mutate global store state, not self-contained models.

Separate OOP model: src/components/Scenario/Workflow/observation/state/Notebook.ts is an UNRELATED self-contained Notebook class wrapping NotebookState {notebook_id, title, cell_count, cells?: NotebookCell[], ...} with encapsulated getters/setters (setCells, addCell, updateCell, toJSON). Its NotebookCell is a DIFFERENT, snake_case, narrower shape (type only 'code'|'markdown'; enable_edit, execution_count, language, could_visible_in_writing_mode). It is part of Workflow observation InternalState (new Notebook(data.notebook)) and is NOT wired to the editor Zustand store — it is a server/agent-state mirror.

### Migration concerns
- Inverted source of truth: cells[] is canonical and the PM/TipTap doc is derived; the 'OOP model, no internal store, external state' goal needs the PM document (or an external OOP model owning a PM doc) to BECOME canonical. - ViewModels call useStore.getState() directly for nearly all writes (updateCell, delete, type-convert, editing state). Removing the internal store means redirecting every one to an injected external model/dispatch — touches BaseCellViewModel and every per-cell ViewModel
- tasks/phases/steps are derived from markdown headings via parseMarkdownCells and re-stamped onto cells on every edit. A PM-first model must reproduce heading->phase derivation (or move it to a PM plugin) without the array-rebuild side effects
- outputs live on the cell, JSON-string-serialized, with injected sentinel entries. Mapping outputs onto PM node attrs or a side-table keyed by cellId must preserve serialize/deserialize + error-sentinel behavior UI depends on
- The default H1 title cell (metadata.isDefaultTitle) is special-cased in many actions; in a PM doc it should be the first heading node, but the protective logic and title<->notebookTitle two-way sync must be reimplemented
- Persistence/autoSave and notebookOrm assume the {cells:Cell[], tasks:Task[]} snapshot; a PM-first model changes the serialized format and needs a back-compat reader for existing IndexedDB notebooks
- Cross-cell navigation/focus relies on window CustomEvents and direct CodeMirror/DOM queries (data-cell-id selectors) rather than a model API — must become PM transactions/commands
- 112 importers of notebookStore form a wide blast radius; Workflow agent write paths (addNewCellWithUniqueIdentifier/updateCellByUniqueIdentifier) must also be redirected to the new model
- Code cells render in CodeMirror, not PM; a PM-first canonical doc must embed code cells as PM nodes whose content is owned by CodeMirror NodeViews, keeping the two editors' state coherent

### ProseMirror mapping
Target: make a ProseMirror document the canonical notebook, owned by an external OOP NotebookModel (no internal Zustand cell array). Mapping: each current Cell becomes a top-level PM block node keyed by a stable cellId attr — markdown cells as native PM rich-text nodes, code/hybrid/image/link/thinking cells as custom atom/leaf nodes with NodeViews (code cells delegate content to CodeMirror NodeViews). Cell.content (markdown string) maps to PM inline content for text cells and to a node attr/CodeMirror buffer for code cells. outputs/enableEdit/phaseId/description/metadata become node attrs or a side-table keyed by cellId for large/serialized outputs. Tasks/phases/steps become a DERIVED projection computed from heading nodes via a PM plugin instead of re-stamping phaseId onto stored cells. The external NotebookModel exposes intent methods (addCell, updateCellContent, setOutputs, convertType, move, delete, navigate) that dispatch PM transactions; ViewModels are refactored to call this injected model API instead of useStore.getState(). React subscribes to PM state (or model events) rather than Zustand selectors; ephemeral UI state (expanded/hovering) stays local in ViewModels. The convertCellsToHtml/convertEditorStateToCells bridge is eliminated (no second array to sync); persistence serializes the PM doc with a back-compat import from the legacy {cells,tasks} snapshot. The Workflow observation Notebook.ts class is a useful precedent for the encapsulated-OOP style but is a separate server-state mirror; the new editor model should be distinct and PM-backed, not built on that snake_case NotebookCell shape.

## Markdown parsing and serialization (TipTap notebook editor)

### Current design
Markdown is NOT handled by a real AST in the editor round-trip — it is entirely regex/string-hand-rolling and DOM-walking. The pipeline is cell-based: a notebook is an array of typed cells (markdown/code/hybrid/image/thinking/link/raw), each carrying a raw markdown/content string. The TipTap editor never sees raw markdown; instead convertCellsToHtml (cellConverters.ts) turns each cell into HTML — markdown cells go through convertMarkdownToHtml (markdownConverters.ts), other cell types become custom <div data-type='...'> node placeholders. convertMarkdownToHtml is line-by-line regex: it extracts images and LaTeX into placeholder tokens first, detects GFM tables via two regexes (row + separator) and recurses, then splits on blank lines into paragraphs and applies inline regex for **bold**/*italic*/`code`/- lists/> quote/#{1,6} headings, finally re-substituting the placeholders. Going back, convertEditorStateToCells reads editor.state.doc.toJSON() and walks ProseMirror nodes: custom node types (executableCodeBlock, markdownImage, thinkingCell, rawBlock, fileAttachment, title, heading) become their own cells, and runs of paragraph/other nodes are serialized to markdown text by extractTextFromNode (handles only bold/italic/code marks, blockquote, bullet/ordered lists, hardBreak, latexBlock, markdownImage) and accumulated into markdown cells. ### Migration concerns
- NO real markdown AST in the round-trip: GFM tables, nested lists, ordered lists, task lists, fenced code inside markdown text, setext headings, reference links, HTML blocks, escapes, and autolinks are all either regex-approximated or silently flattened. A PM-first design needs a genuine mdast (remark) <-> ProseMirror bridge to avoid perpetuating loss.
- Code fences are NEVER parsed from markdown text — code is a separate cell type. A markdown cell containing a ```python block is treated as literal paragraph text (backticks survive only because inline `code` regex is non-greedy per line). Round-tripping a fenced block through the editor will corrupt it. In PM, code blocks must be first-class nodes parsed from fences.
- Frontmatter is write-only: exportToMarkdown emits YAML frontmatter, but no import path (parseMarkdownContent, importCustomNotebook, importJupyterNotebook) parses or strips it — re-importing an exported .md would treat '---' as a thematic break / literal text. Frontmatter is asymmetric and lossy.
- Math: inline vs block ($...$ vs $$...$$) detection is heuristic (whole-line trim match) and collapses lone-line inline $...$ into display mode; extractTextFromNode re-emits based on displayMode attr, so a single-line inline formula round-trips as block. Empty/multi-$ expressions ([^$]+ forbids nested/empty) break the regex.
- Custom blocks (executable-code-block, thinking-cell, raw-block, file-attachment, markdown-image) have no markdown representation at all — they only survive as TipTap data-attribute HTML / cell types. Exported markdown loses thinking cells, raw cells, generation metadata, and code outputs entirely (export only stringifies content). PM migration must define canonical node specs + (de)serializers for each.
- Thinking blocks: thinking cells carry no content (content:'' in both converters) and agentName/textArray/customText are written to HTML attrs but discarded on the way back (commented out in fallback). State is effectively non-round-trippable and must be redesigned as a real node with persisted attrs.
- URI-encoded JSON in HTML attributes (code, outputs, generationParams) is fragile (double-encoding, attribute-quote injection via unescaped data-markdown="${markdownContent}") and must be replaced by ProseMirror node attrs.
- Table parsing requires the separator row regex to match exactly; alignment (:---:) is detected but dropped on output (always '---'); cells split naively on '|' so escaped \| or pipes inside inline code break parsing.
- Heading round-trip rewrites levels: import re-levels headings via titleStack, and convertEditorStateToCells splits every heading into its own cell — original heading nesting/level intent is not preserved faithfully.
- HTML escaping is absent: convertMarkdownToHtml injects raw text into innerHTML-style strings (e.g. <p>${text}</p>, table cells, alt/src attrs) with no escaping, so '<', '&', or quotes in user markdown produce malformed HTML and silent loss on the return trip.

### ProseMirror mapping
Adopt a ProseMirror-first model where the document IS the ProseMirror doc and markdown is just one (de)serialization format. (1) Replace convertMarkdownToHtml / convertHtmlToMarkdown / parseMarkdownContent with a remark (mdast) <-> ProseMirror bridge: parse markdown to mdast with remark-parse + remark-gfm + remark-math + (a frontmatter plugin) and map mdast nodes to PM nodes; serialize PM->markdown with prosemirror-markdown (custom MarkdownSerializer) or remark-stringify. This makes GFM tables (with alignment), fenced code blocks, ordered/nested/task lists, frontmatter, and math first-class and lossless. (2) Model each current cell type as a PM node spec with explicit attrs instead of data-attribute HTML: code_block (from fences, with language + outputs attr), math_inline/math_display, image, thinking node, raw node, file_attachment, title — each with toMarkdown/parseMarkdown hooks (or a sidecar fenced ```{thinking} custom-container syntax via remark-directive for blocks that have no native markdown). (3) Derive the Task/Phase/Step outline from PM heading nodes via a ProseMirror plugin/decoration walking the doc, removing the per-mutation parseMarkdownCells regex pass in the store. (4) Keep cells[] only as an export/interop projection generated from the PM doc, or drop it entirely in favor of PM JSON as the source of truth, with a single cellsFromDoc/docFromCells adapter for Jupyter/JSON import-export. (5) Centralize escaping in the serializer so arbitrary text can never produce malformed output. This collapses the four overlapping conversion paths (MD->HTML regex, HTML->MD DOM walk, PM-JSON->MD extractTextFromNode, DOM fallback) into one canonical PM<->mdast layer.

## Code Execution, AI Streaming, and Output Rendering

### Current design
Single source of truth is the Zustand notebookStore.cells: Cell[] flat array. A Cell carries content (string, the editable code/markdown), outputs: OutputItem[] (read-only execution results), metadata (record), type, enableEdit, plus ad-hoc fields via an open index signature. Execution: CodeCell -> ViewModel.execute -> codeStore.executeCell(cellId). codeStore initializes a global kernel (notebookId), clears outputs, sets per-cell exec state (isExecuting/elapsedTime in codeStore.cellExecStates, keyed by cellId, NOT on the cell), starts a 1-second polling loop (getExecutionStatus) that streams partial outputs into the cell via notebookStore.updateCellOutputs, and awaits the executeCode HTTP call whose final result.outputs overwrite the cell outputs, then triggerAutoSave. There is NO websocket/SSE for code execution; it is request/response + polling. Outputs are written through updateCellOutputsHelper which sanitizes, serializes object content to strings, and PREPENDS a sentinel marker ([error-message-for-debug] when any output.type==='error', or [without-output] when empty) as outputs[0]. Rendering: OutputDisplay maps cell.outputs through processOutput then OutputRenderer, dispatching by output.type (text/error -> ansi_to_html in <pre>; image -> <img>; html -> dangerouslySetInnerHTML). showAIdebug is derived by checking outputs[0].content === '[error-message-for-debug]'. Display mode (COMPLETE/CODE_ONLY/OUTPUT_ONLY) lives in codeStore.cellModes keyed by cellId and controls whether editor/output render. AI streaming uses a SEPARATE pipeline: a registry of StreamAction handlers (services/stream/actions/*) dispatched by a stream message 'type'. Cell-content streaming (addNewContent2CurrentCell, tiptap_update) appends text to cell.content via read-modify-write updateCell. Cell creation/metadata streaming (addCell2EndWithContent, updateCurrentCellMetadata, setCurrentCellMode_*) mutate the store; async generation tasks are correlated to cells via a GenerationTracker (commandId/uniqueIdentifier -> cellId) and finalized by metadata updates (isGenerating/generationCompleted). Server can drive execution via runCurrentCodeCell (-> runSingleCell -> executeCell) and exec/exec_new_version (workflow path via useScriptStore.execCodeCell). AI prose answers stream to a DIFFERENT store (AIAgentStore.qaList via globalUpdateInterface.addContentToAnswer) and render in the right-sidebar QA view, not in the notebook document. The active editor (default editorType='tiptap') is TiptapNotebookEditor: the PM doc holds CodeBlock nodes whose attrs include cellId/code/outputs, but the CodeBlock NodeView ignores its own outputs attr for live cells and looks the cell up in Zustand by cellId, rendering the same React CodeCell. useEditorSync reconciles store->doc and rebuilds the doc when a cell's content or outputs change. So even under TipTap, outputs and execution state live in Zustand, and PM node attrs are a serialization mirror.

### Migration concerns
- Outputs must become a read-only, non-editable region of the codeCell node. Today they live in Zustand, not in the PM doc; in a PM-first design they should be node attrs (or an atom child node) with selectable=false / contentEditable=false, but the in-band sentinel markers ([error-message-for-debug]/[without-output]) must be replaced by a structured execution-status field or the UI's showAIdebug/empty logic will break.
- Per-cell execution runtime state (isExecuting/elapsedTime/isCancelling) currently lives in codeStore.cellExecStates keyed by cellId, decoupled from the cell. PM transactions are synchronous and serializable — storing rapidly-changing elapsedTime as a node attr would spam transactions/history. Need an out-of-band ephemeral state (plugin state / decorations / external store) keyed by a stable node id, plus a stable cell identity that survives PM position changes.
- The 1s polling loop writes partial outputs via updateCellOutputs many times during a run; under PM each write becomes a transaction (and would pollute undo history). Output/exec updates must be dispatched with addToHistory:false (or kept in plugin state) and debounced.
- Stable cell identity: cellId currently links Zustand cell <-> PM node <-> generationTracker <-> autosave. PM nodes have no inherent stable id; the migration must guarantee cellId uniqueness/persistence across splits, merges, paste, and collab, since async streaming (generationTracker, updateCurrentCellMetadata) resolves targets by cellId/uniqueIdentifier and a lastAddedCellId fallback.
- Executor injection: CodeExecutionService is a static singleton hard-wired to global fetch endpoints and a single global kernel. A PM-first executor should be injected (per-editor service) so node commands (executeCell) call an abstract executor, decoupling schema from the HTTP/kernel transport and enabling test mocks.
- Streamed content append (addNewContent2CurrentCell / tiptap_update) currently does read-modify-write of the entire content string. In PM this should be incremental insertText transactions at the node boundary; full-string replacement every token would be O(n^2) and destroy cursor/selection. Replace vs append semantics must be preserved.
- Two execution code paths (interactive codeStore.executeCell vs workflow useScriptStore.execCodeCell with effect-clearing + debug metadata) must be unified or both routed through the injected executor command, or the workflow path will diverge from the PM node command.
- AI prose answers (addContentToAnswer -> AIAgentStore qaList -> sidebar) are outside the document model; decide whether they remain a side channel or become document nodes. Migration scope should explicitly exclude/retain this to avoid conflating QA streaming with cell streaming.
- Display mode is dual-stored (codeStore.cellModes vs metadata.displayMode); pick one (node attr) during migration to avoid the existing divergence.
- Output content is string-coerced everywhere, losing structured/rich (Jupyter MIME bundle) outputs. If richer outputs are desired post-migration, the outputBlock schema should model {mimeType, data} rather than {type, content:string}; otherwise preserve the current string contract to avoid breaking renderers (ansi_to_html text, dangerouslySetInnerHTML html, img src image).
- useEditorSync rebuilds the doc on any output JSON diff (full stringify); a PM-first model where outputs are node attrs would let PM diff natively, but the store->doc reconciliation must be retired carefully to avoid double-write loops with autosave.

### ProseMirror mapping
"Model a codeCell PM node with attrs { cellId (stable persistent id), language, enableEdit } whose editable text content is the code (an editable text node / code-content child), plus a sibling/child outputBlock node that is an atom (atom:true, selectable:false, draggable:false) holding outputs as a structured attr: { items: [{ kind:'text'|'error'|'html'|'image', data:string, mime? }], status:'ok'|'error'|'empty', executionCount? }. Execution runtime state (isExecuting/elapsedTime/isCancelling) should NOT be node attrs (they change too fast and would pollute history); keep them in a ProseMirror plugin state or external ephemeral store keyed by cellId, surfaced via decorations on the node. ## React view layer and external-state (Zustand) boundary of the TipTap notebook editor

### Current design
Single source of truth is the Zustand store's `cells: Cell[]` (src/store/notebookStore.ts). The TipTap editor is a *derived view* over that array, with bidirectional sync mediated entirely inside React.

Mounting chain: NotebookApp -> useContentResolver -> WorkspacePage -> (viewMode==='create') CreateMode -> TiptapNotebookEditor. CreateMode picks tiptap vs jupyter from settingsStore and gates on `isLoaded`. NotebookApp/WorkspacePage/useCellRenderer/useContentResolver are NOT part of the editor's internal text model at all — they render *non-editor* cell components (CodeCell, MarkdownCell, ImageCell, etc.) for 'demo'/'complete' view modes via `renderCell`. Only 'create' mode mounts the actual TipTap editor. So there are effectively two rendering paths over the same `cells` array: (1) the TipTap rich-text editor (create mode), (2) plain React cell components (demo/complete modes).

TiptapNotebookEditor.tsx is the real integration point. It:
- reads `cells`/`setCells` from the store via selectors,
- computes `initialContent` once via convertCellsToHtml(cells) (empty deps),
- creates the editor with `useEditor({ extensions, content, onCreate/onUpdate/onBlur/onTransaction/onDestroy })`,
- holds the editor in a local `useRef` (editorRef) and local `useState` (currentEditor) — `setCurrentEditor` is just the local setState, the instance never leaves React,
- wires the sync hooks and exposes an imperative ref API (getCells/setCells/addXCell/focus/getHTML).

Sync direction store->editor (useEditorSync.ts): a useEffect diffs `cells` against `lastCellsRef`; if structure/content changed it sets `isInternalUpdate.current=true`, runs `convertCellsToHtml(cells)` and `editor.commands.setContent(html, false)` deferred via setTimeout, then releases the lock after 50ms. A second effect does a lightweight 'thinking cell' signature refresh.

Sync direction editor->store (useEditorEvents.ts): onUpdate debounces 50ms, runs `convertEditorStateToCells(editor)` (reads editor.state.doc.toJSON()), diffs against `cells`, and either `setCells(mergedCells)` for structural changes or `updateCell(id, content)` for markdown-only diffs, guarded by the same `isInternalUpdate` lock. onBlur/onDestroy/beforeunload force an immediate final sync. `mergeCellsWithStore` re-reads `useStore.getState().cells` to preserve code-cell outputs that the HTML round-trip would lose.

The whole contract between React and the framework-free core is therefore two pure functions in src/components/Editor/utils/cellConverters.ts: convertCellsToHtml (cells->HTML/doc) and convertEditorStateToCells (doc JSON->cells), plus the `isInternalUpdate` reentrancy lock and TipTap lifecycle callbacks.
